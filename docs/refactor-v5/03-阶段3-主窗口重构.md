## 1. 这一阶段解决的问题

Phase 1 审计发现：缺的 5 项（D）全部集中在**"时间语义可见化"**。

用户看到的数字是模型估计，但界面上没有任何线索告诉他：

- 这个数是**几点**的？
- 我上次自评是**多久以前**？
- 它比我的基线**高多少**？

于是"两小时前自评 + 模型推演到现在"会被读成"我刚说过"。

Phase 2 把数据修对了（读数跟着曲线走），Phase 3 负责**把它说出来**。

---

## 2. 首屏：一行 meta 说清三件事

`StateHead` 增加一行：

```
距上次自评 12 分钟 · 模型估计 14:32 · 比基线 +12
```

| 信息 | 来源 | 说明 |
|---|---|---|
| 距上次自评 | `state_ts - last_obs_ts` | 不需要额外参数——`state_ts` 在衰减/刷新路径上就等于 `now` |
| 模型估计时刻 | `state_ts` | 只在「模型比自评新」时才显示，否则是废话 |
| 与基线差 | `valence - baseline_v` | ≤2 说"与基线持平"，避免 ±1 的噪声被当趋势 |

**边界处理**：

| 情况 | 显示 |
|---|---|
| `state_ts == 0`（无状态） | 空字符串，不占视觉噪声 |
| 距上次自评 < 60s | "刚刚自评"（不写"0 分钟"） |
| 从未自评 | "还没有自评" |
| 基线未知 | 省略差值段 |

这一行的意义不只是信息量：**它是三种数据（真实观察 / 模型估计 / 未来预测）在文字层唯一的界标**。曲线上的区分（实心点/实线/虚线）在窄窗口里看不清，文字不会。

---

## 3. 曲线：用户修正点有了自己的形状

之前 `_edits`（用户拖动纠正）只影响重拟合结果，**画面上看不出来改过哪里**。用户改完再打开，分不清哪个点是原始观察、哪个是自己改的。

现在四种元素四种画法：

| 元素 | 画法 | 数据来源 |
|---|---|---|
| 真实观察 | 实心小圆（弱） | `payload["raw"]` |
| 模型估计 | 实线 + ±1σ 置信带 | `payload["mv"] / vv` |
| 未来预测 | **虚线**（与实线相接） | `predicted_from` 之后 |
| **用户修正** | **空心方框** | `payload["corrections"]`（新增） |

修正标记按维度过滤（`channel == "valence" / "arousal"`），效价面板只画效价的修正，唤醒面板只画唤醒的。

`presenter.correction_marks()` 统一产出，历史曲线与衰减尾巴两条路径都带。

## 4. 视图不再自己拼模型内部数据

**改前**（`main_console._open_correction_sheet`）：

```python
sheet = CorrectionSheet(
    timestamps=self.observations_ts_for_curve(),        # 转发
    model_v=[s.valence for _, s in self.states],        # 视图自己遍历
    model_a=[s.arousal for _, s in self.states],
    baseline_v=self.baseline_ctrl.current.valence,      # 摸模型内部
    current_state=self.states[-1][1],
)
```

**改后**：

```python
ctx = self.presenter.correction_context()
if not ctx["has_data"]:
    return
sheet = CorrectionSheet(**ctx)   # 语义化 bundle
```

`correction_context()` 返回 `{has_data, timestamps, model_v, model_a, baseline_v, current_state}`——视图只消费，不组装。

### 顺带清理：3 个无人使用的转发属性

Phase 1 点名了 `main_console.py` 的 14 个转发属性。逐条核对真实使用后：

| 属性 | 生产代码 | 测试 | 处理 |
|---|---|---|---|
| `_segment` | 0 | 0 | **删除** |
| `_last_obs_ts` | 0 | 0 | **删除** |
| `_decay_now` | 0 | 0 | **删除** |
| `states` / `params` / `calibrator` / `baseline_ctrl` | 传给子控件的 provider | — | 保留 |
| `_wave_active` / `_edits` / `observations` / `recording` / `estimator` / `timer` | 0 | 有 | 保留（测试缝） |

**诚实修正 Phase 1 的措辞**：那 14 个属性里，生产 UI 其实只用到 4 个，其余是**测试缝**而非活跃的越界依赖。真正的问题是"接口缺位导致测试只能摸内部"，已在 §4 用 `correction_context()` 开了头。剩余测试缝保留，并在代码里加了注释说明它们的身份，避免下一轮又当成违规来查。

## 5. 明确没做：时间范围选择（6h / 24h / 7d）

你方案 UI-1 里提到"可以考虑 6 小时 / 24 小时 / 7 天"，并补了一句"具体选项应该根据实际数据密度和查询能力确定，不要为了好看而生成大量没有实际意义的数据点"。

**本轮不做，理由三条**：

1. **数据密度不够**。当前一波结束即清空 `observations`，跨事件只有 `emotion_events.raw_data`。一天通常 3–5 个事件、每个几十个点，中间是数小时空档。
2. **RTS 在多小时空档上会退化成"往基线插值"**。画出来是一条贴着基线的平线加几个尖峰——这正是你说的"没有实际意义的数据点"。
3. **体积预算**。跨事件重建 + 选择器 + 测试约 200 行，当前余量要留给 Phase 4/5。

**留到 Phase 6**：用真实使用数据算一下"事件之间的空档分布"，如果一天有 10+ 次自评，再决定要不要做、用什么平滑方式（可能需要分段而非全局 RTS）。

接口侧已就绪：`query_curve(start_ts, end_ts, resolution)` 支持窗口与分辨率，只差数据源。
