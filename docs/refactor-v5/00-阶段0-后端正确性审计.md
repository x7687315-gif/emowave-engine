## 0. 总体结论

三条线索**全部证实存在**，其中两条是 P0：

| 编号 | 问题 | 判定 | 严重度 |
|---|---|---|---|
| A | 恢复状态后重复推进模型时间 | **已确认 Bug** | P0 |
| B | `latest_state` 与曲线尾巴不同步 | **已确认 Bug** | P0 |
| C | 重复定义 / 接口副作用 | **已确认**（含 1 处假阳性已排除） | P1 |

**A 和 B 是同一个根因的两个症状**：

> 系统里存在**两套并行的时间推进**——`StateEstimator`（由 `query_state()` 推进）和 `_tail`（presenter 自己的增量外推）。
> 两者各自维护一份状态，各自前进，从不互相校对。

- 曲线画的是 `_tail`；
- 读数和挂件读的是 `latest_state`（来自 estimator）。

于是"曲线在衰减、数字不动"，"恢复后尾巴整体平移"。这不是两处独立的小毛病，而是一处架构裂缝。

## 1. 问题 A：恢复后重复推进模型时间

### 1.1 判定：**已确认 Bug（P0）**

### 1.2 调用链

```
ConsolePresenter.resume_active_wave()              console_presenter.py:505
  ├─ for ts,v,a in samples: estimator.update(obs)    → 模型时间 = last_obs_ts
  ├─ state = self.query.query_state()               → query_state() 内部：
  │     StateQuery.query_state()                     state_query.py:56
  │       └─ est.advance_to(target=now)              → 模型时间 = now（副作用！）
  └─ timer.start(1000)
        └─ decay_step()                              console_presenter.py:306
              └─ _tail_points(horizon)               console_presenter.py:351
                    └─ self._tail = {"x": estimator.state_vector, ...}
                       ↑ 起点是**已经推进到 now 的状态**
                    但点的标签是 self._last_obs_ts + k*DECAY_DT
                       ↑ 从 last_obs 开始编号
```

**时间被推进了两次**：一次由 `query_state()` 推到 `now`，一次由 `_tail_points()` 再推 `horizon` 秒。
而 `_tail_points()` 给这些点打的时间戳却从 `last_obs_ts` 起算——所以尾巴的值和标签差了整整一个 `horizon`。

### 1.3 实测证据

场景：5 条 1Hz 自评（v=0.90, a=0.85）→ 停止记录 → 关机 60 秒 → 新建 presenter → `resume_active_wave()` → `decay_step()`。

```
停止记录时：last_obs_ts=1700000005.0  estimator.last_timestamp=1700000005.0
resume 之后：now=1700000065.0  estimator.last_timestamp=1700000065.0  (被推进了 60.0s)
  模型状态 v=0.8822  ← 已是「现在」的值

  尾巴点数=60  首点 ts=1700000006.0 (距 last_obs 1.0s)  v=0.8817
  尾点 ts=1700000065.0 (距 last_obs 60.0s)  v=0.8449

  正确参照（从 last_obs 推 60s）: v=0.8823
  → 尾巴首点(标称 1s) v=0.8817 ，偏差 0.0006
  → 若从 last_obs 推 120s 才得到 v=0.8450（对比首点 v=0.8817）
```

**读法**：标称"距 last_obs 1 秒"的那个点，值其实是"距 last_obs 60 秒"的值（0.8817 ≈ 0.8823）。
尾巴末点标称 60s，值 0.8449，实际等于 120s（0.8450）。

**整条尾巴被平移了 `horizon` 秒，平移量 = 关机时长。** 关机 30 分钟，尾巴就平移 30 分钟。

### 1.4 用户可见后果

1. 重开应用后，曲线在最后一次自评处**垂直跳变**（从 0.90 掉到 0.88 再继续往下），看起来像"记录完突然崩了一下"；
2. 尾巴的时间轴与真实时间错位，用户读不出"现在是几点对应的状态"；
3. 关机越久，错位越大——正好违背 v4 要修的"按真实经过时间外推"。

### 1.5 为什么 v4 的测试没抓到

`test_decay_tail_matches_from_scratch` 断言的是"增量推进 == 从零重算"。但 `_decay_points()` **也**从 `estimator.state_vector` 起算——两边同样错，所以断言成立。

> 这是一条通用教训：**两个实现互相印证，只能证明它们一致，不能证明它们正确。**

## 2. 问题 B：`latest_state` 与曲线尾巴不同步

### 2.1 判定：**已确认 Bug（P0）**

### 2.2 根因

`decay_step()` 只更新 `_tail` 和曲线，**从不更新 `latest_state`**。
而 `_readout_payload()`（`console_presenter.py:829`）优先读 `latest_state`：

```python
st = self.latest_state or (self.states[-1][1] if self.states else None)
```

`latest_state` 只在三处被写：`resume_active_wave()`、`_refresh_now()`、`restore_recent_context()`。
而 `_on_refresh()` 在 `_wave_active` 为真时**直接 return**——衰减动画全程，没有任何代码更新它。

### 2.3 实测证据

```
horizon≈ 10s | latest_state.ts距last_obs=   0.0s v=0.9000 | 尾巴末点 ts距last_obs=  10.0s v=0.8992
horizon≈ 60s | latest_state.ts距last_obs=   0.0s v=0.9000 | 尾巴末点 ts距last_obs=  60.0s v=0.8822
horizon≈200s | latest_state.ts距last_obs=   0.0s v=0.9000 | 尾巴末点 ts距last_obs= 200.0s v=0.7861
horizon≈400s | latest_state.ts距last_obs=   0.0s v=0.9000 | 尾巴末点 ts距last_obs= 400.0s v=0.6641
```

**读数全程冻结在 0.9000、时间戳停在最后一次自评**，而曲线已经衰减到 0.6641。
两者相差 0.24——在 0–1 的效价尺度上，这是"偏高"和"中性偏正"的区别。

### 2.4 用户可见后果

1. **主窗口数字与自己的曲线矛盾**：曲线往下走，数字不动。用户会怀疑哪个是真的。
2. **挂件同步冻结**：挂件读同一份 `latest_state`，所以它也不动——"持续状态视图"名不副实。
3. `_end_wave()` 之后 `latest_state` 的时间戳仍是 `last_obs`（实测距 now 400s），
   界面上这是一个"400 秒前的状态"被当作"当前状态"展示。

### 2.5 与 A 的关系

A 是"尾巴被多推了一段"，B 是"读数根本没推"。两者都源于 `_tail` 与 estimator 双轨制：

| 数据 | 来源 | 谁推进它 |
|---|---|---|
| 曲线（历史） | `RTSSmoother` | 数据变化时全量重算 |
| 曲线（预测尾） | `_tail` | `decay_step()` 每 tick |
| 读数 / 挂件 | `latest_state` ← estimator | `query_state()`，但衰减期间不调用 |

**三份数据、两个时间源、零次校对。**

| 位置 | 初判 | 复核结论 |

AST 扫描无法区分 property 与普通方法，按名字计数会误报。**记录在此，避免下一轮重复怀疑。**

### 3.3 接口副作用（设计问题，非 Bug）

`StateQuery.query_state()` 的 docstring 写着：

> "查询是只读语义，不该因为毫秒级竞态把调用方打断。"

但实现调用 `est.advance_to(target)`，**会永久改变 estimator 的 `_last_timestamp` 和状态向量**。

| 维度 | 实际行为 |
|---|---|
| 名字 | `query_*` → 暗示只读 |
| 行为 | 推进模型时间（写操作） |
| 返回值 | 目标时刻的 `EmotionState` |
| 目标早于当前 | 返回 `current_state()`，不报错（`advance_to` 本身会 `raise ValueError`） |

**这就是 A 的直接诱因**：`resume_active_wave()` 以为自己在"读一下现在"，实际把模型推到了 now，随后的尾巴又从 now 起算。

按你的要求，本阶段只审计，**不拆接口**。最小修法见 §4。

## 4. 最小修复方案

原则：**不动数学模型、不重写估计器、不引入新框架**。

### 4.1 修 A + B 的共同根因：让尾巴成为唯一时间源

**方案**：衰减期间，不再让 `_tail` 维护独立的 `x/P`，而是**直接推进 estimator**，尾巴只保存点序列。

```python
# 现状（双轨）
self._tail = {"x": estimator.state_vector, "P": estimator.covariance, ...}
tail["x"], tail["P"] = predict_step(tail["x"], tail["P"], ...)

# 改为（单轨）
state = self.estimator.advance_to(now)     # 唯一的推进
self._tail_pts.append((now, state.valence, state.arousal,
                       state.variance_valence, state.variance_arousal))
self.latest_state = state                  # 顺手解决 B
```

收益：

1. **A 自动消失**：`advance_to` 内部按 `last_timestamp` 算增量，不可能重复推进；
2. **B 自动消失**：读数与曲线尾巴来自同一个 `state` 对象；
3. **代码变短**：删掉 `_tail["x"]` / `_tail["P"]` / `predict_step` 调用，presenter 约 −25 行；
4. **语义统一**：v4 已经让 `_predict` 在偏离空间传播（回基线），与 `predict_step` 数学一致，可以合并。

风险与对策：

| 风险 | 对策 |
|---|---|
| `advance_to` 每 tick 只推 1s，粒度由墙钟决定（不再固定 `DECAY_DT`） | 这正是想要的：时间跟墙钟。点数 = 实际 tick 数 |
| 长间隔（如 30 分钟）一次 tick 推 1800s | `advance_to` 已按 600s 分段，单次成本 O(间隔)，可接受 |
| 曲线点可能不均匀（tick 抖动） | 视图按时间戳映射到像素，本身不要求等距 |

### 4.2 修 `query_state` 的副作用

**不加新接口，只改文档与调用方式**：

- `resume_active_wave()` 不再调 `query_state()`——尾巴会推进，不需要提前推；
- `query_state()` 的 docstring 改成明确写"**会推进模型时间**"，并注明"只读场景请用 `current_state()`"。

> 是否拆成 `query_state`（只读）+ `advance_to`（写）两个入口，留到 Phase 2 按 UI 需求决定。
> 现在拆属于"为了统一形式而重构"，违反最小必要原则。

### 4.3 修 C

纯删除，无行为变化：

- 删 `showEvent` / `_tail_points` / `restore_recent_context` 各一份（保留最后一份，即当前生效的那份）；
- 删 `_tail = None` 的两处重复；
- 删 19 个重复测试 + 1 个重复 helper。

**验收**：删除前后 `709 passed` 不变（因为跑的一直是后一份）。

### 4.4 必须新增的回归测试

| 测试 | 断言 | 为什么现有测试抓不到 |
|---|---|---|
| `test_resume_does_not_double_advance` | 关机 60s 后恢复，尾巴首点值 ≈ 从 last_obs 推 1s 的值（而非推 61s） | 现有测试只比对两个同样错的实现 |
| `test_latest_state_tracks_tail_during_decay` | 衰减 400s 后 `latest_state.valence == 尾巴末点 valence`（1e-9） | 现有测试只看 `latest_state is not None` |
| `test_latest_state_timestamp_follows_clock` | 衰减中 `latest_state.timestamp == now` | 从未断言时间戳 |
| `test_no_duplicate_definitions` | AST 扫描：模块级/类级无同名函数（排除 property+setter） | 无此类护栏 |
| `test_resume_curve_is_continuous` | 恢复后尾巴首点与历史末点差值 < 0.01 | 从未检查连续性 |

最后一条建议做成**架构护栏**（和 v4 的"无孤儿模块"同级），防止重复定义再次潜入。

## 7. 复现方式

```python
clock = FakeClock(); p = ConsolePresenter(db=db, clock=clock)
p.toggle_recording(True)
for _ in range(5): clock.advance(1); p.sample(0.90, 0.85)
p.toggle_recording(False)
clock.advance(60)                      # 关机 60 秒
p2 = ConsolePresenter(db=db, clock=clock); p2.resume_active_wave()
p2.decay_step()

```

无需真实等待，全部确定性。
