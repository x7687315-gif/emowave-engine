## 1. 先回答用户的问题：尾巴为什么变这么多

不是"某一次改动写多了"，而是**两次架构迁移都没有收尾**，加上**研究脚手架只增不减**，三股叠加：

| 来源 | 机制 | 规模 |
|---|---|---|
| ① 1.x 引擎栈没退役 | 2.0 把内核重写成 `emowave/core/**`（零依赖），但根目录的 `engine.py` / `kalman_filter.py` / `predictor.py` / `threshold.py` / `baseline.py` / `recommender.py` / `annotator.py` / `config.py` / `session.py` 一直留在原地。它们**对出货 UI 零引用**，只被"自己的脚本式测试"续命 | ~2.8k 行 |
| ② 研究/评估脚手架越堆越多 | 数据合成、基准、评估、白皮书、性能剖析、引导、危机协议各写一份独立脚本，彼此互相 import 成自闭闭环。它们**对 `main_app.py` 与 `emowave.cli` 零引用**，却把 `numpy` 拖进了 `requirements.txt` | ~9.9k 行 |
| ③ 死窗口 + 一次性产物 | `console_window` / `dashboard_window` / `surfing_window` 已被 `main_console` 取代；`privacy_export` / `report_generator` 从未接线；`dashboard/`（2.3k 行 HTML）、`research/`、`docs/shot*.py`、`.bak.html` 全是历史残留 | ~3.9k 行 |
| **合计** | — | **≈18.7k 行 / 全仓 41k 行（45%）** |

**关键点：这 18.7k 行里，没有一行是出货路径需要的。** 证据见 §3。

| # | 信息面 | 真实 query | 命中 | 采纳点 |

**结论（三角验证后的三条纪律）**：
1. **删除前先打锚点**：`tag` 是"源码仍可取回"的唯一低成本手段，等价于归档但不占工作树（来源 #1 官方 README 的"跑库+测试"、#7 的 git 语义）。
2. **证据要双份**：AST 可达图（结构证据）+ 独立 grep（文本证据），两者一致才动手（来源 #2）。
3. **删完要装护栏**：只删不防，尾巴必然再长。用"零依赖内核契约 + 孤儿模块守卫"把它固化成测试（来源 #3/#4/#5）。

> 未能核实项：本仓库无 `gh` CLI，Issues/Discussions 两个面只做到语义检索 0 命中，标注为**待验证**，不作为结论依据。

## 4. 精简原则（本轮的"宪法"）

1. **出货路径优先**：`main_app.py` + `emowave.cli` + `emowave/core` 是不可动的三根柱子。
2. **删除必须可回滚**：动手前打 `archive/v1-legacy-2026-10` tag；每个波次一个独立 commit，单条 `git revert` 可撤。
3. **每波必过绿测门禁**：删除前后 `pytest -q` 结果必须一致（除"随删除一起退役的测试"）。
4. **只删不改逻辑**：本轮不重写算法，避免把"瘦身"做成"重写"。
5. **删完装护栏**：把"什么算孤儿""内核不许依赖第三方"写成测试，尾巴无法再悄悄长回来。
6. **文档同源**：每个阶段一份 MD，写完即 commit + push，进度可查。
