# 阶段 3 · Wave C：架构护栏（让尾巴无法再长回来）

> 日期：2026-10-17 · 基于 `99d032b`（Wave B）

---

## 1. 为什么必须做这一步

前两波删掉了 18.7k 行，但如果**没有任何机制阻止**，下一次"先留着吧""以后再接"
就会把尾巴重新养回来——这正是这次问题的成因。所以瘦身的最后一步不是删，是**上锁**。

调研结论（见阶段 0 台账）：
- `import-linter` 用契约把分层写进 CI（来源 #3/#4）；
- 但它本身是第三方依赖，而本项目的第一原则是**零依赖内核**、依赖清单越短越好；
- 本项目需要的判定只有三条，用 60 行 AST 就能覆盖——**不引入新依赖**。

## 2. 做了什么：`tests/test_architecture.py`（4 条护栏）

| 护栏 | 断言 | 拦住什么 |
|---|---|---|
| `test_no_orphan_modules` | 每个非测试模块都必须从 `main_app` / `emowave.cli` **可达** | 新增却没人 import 的"研究脚本""旧实现" |
| `test_public_api_allowlist_is_still_real` | 白名单里登记的模块必须真实存在 | 白名单腐化成"僵尸名单" |
| `test_core_has_no_third_party_imports` | `emowave/core/**` 只许 import 标准库与 `emowave.*` | 有人往内核里塞 numpy / PyQt5 |
| `test_entrypoints_import_without_display` | 无显示环境下 `main_app` / presenter / 窗口 / 内核可 import | 解耦边界被破坏 |

### 实现要点（都是标准库）

- **相对 import 展开**：`from .engine import X` 需要先回到当前包再拼绝对名，否则
  `presenters/` 内部的依赖边会全部丢失（第一版就是这么漏掉的，护栏误报 29 个孤儿）。
- **祖先包一并算可达**：import `emowave.core.calibration.calibrator` 时，
  `emowave.core.calibration` 与 `emowave.core` 也会被加载。
- **白名单**：`emowave.adapters.storage.sqlite`（699 行，schema 版本化 + append-only
  触发器）是 pip 包对外的存储适配器，**只有测试可达但属于公开 API**，显式登记。
- **标准库判定**：`importlib.util.find_spec()` 的 `origin` 是否落在
  `site-packages` / `dist-packages`，兼容 Python 3.9（此时还没有
  `sys.stdlib_module_names`）。

## 3. 护栏自检（meta-test）

护栏本身也要被验证。临时投毒：

```bash
echo 'X = 1' > _orphan_probe.py
pytest tests/test_architecture.py::test_no_orphan_modules
# → FAILED: 以下模块从 main_app / emowave.cli 不可达，属于孤儿代码：['_orphan_probe']
rm _orphan_probe.py
```

**结论**：护栏确实会在"尾巴"出现的当下就报警，而不是等人肉 review。

## 4. CI 接入

```yaml
- name: "Guard: architecture (zero-dep core, no orphans)"
  run: python -m pytest -q tests/test_architecture.py
```

独立成 step，PR 上红灯直接指向"你引入了孤儿模块 / 内核被污染"，不用翻 600 条测试日志。
