> 日期：2026-10-19 · 基于 `0b241d8`（Phase 5）· 回滚锚点 `v4-phase0`

---

## 1. 做了什么

### 1.1 快照校验：坏数据不许进模型

`SnapshotStore.load_wave()` 以前只挡住"JSON 解析失败"和"空样本"。
但**能解析成 JSON 的坏结构**会直接炸在启动路径上：

```python
for ts, v, a in samples:      # samples 里混进 ["x", 0.5, 0.5] → ValueError
```

新增 `_validate_samples()`，逐条校验并在任何一条不合法时**整体丢弃**：

| 校验 | 拒绝的例子 |
|---|---|
| 必须是 3 元组 | `[["x", 0.5, 0.5]]`、`[[1000.0, 0.5]]` |
| 必须能转 float | `[["x", ...]]` |
| 时间戳为正 | `[[-1.0, 0.5, 0.5]]` |
| v/a ∈ [0,1] | `[[1000.0, 1.5, 0.5]]` |
| 时间戳不乱序 | `[[1000,...], [999,...]]` |
| 条数上限 10000 | 被污染的巨型快照 |

**为什么"整体丢弃"而不是"跳过坏的那条"**：快照是连续序列，
中间缺一条会让 RTS/滤波把缺口当成真实时间间隔，比没有快照更糟。

另外 `last_obs_ts` 也要可信：缺失或早于最后一条样本时，以样本为准。

### 1.2 `resume_active_wave()` 幂等

以前重复调用会把同一批观察插两遍——模型会当成"两次独立证据"。
现在开头加守卫：`if self.observations or self._wave_active: return`。

### 1.3 `update()` 长间隔：不再吞时间

旧写法 `dt = min(dt, 600)` 把 1 小时空档当成 10 分钟——**时间被吞掉**，
与 D2（按真实经过时间推演）直接矛盾。

改成按 `_MAX_PREDICT_DT` **分段推进**：总推进量 = 真实间隔，每步不超过 600s。
生理控制输入只在最后一段施加（否则会被放大 N 倍）。

判据测试：1 小时空档后，纯预测状态应回到基线附近（|v−0.5| < 0.05）；
旧实现会停在约 0.13。

### 1.4 重启后模型接着上次（`restore_recent_context`）

Phase 4 留了个洞：波结束 → observations 清空 → 重启后 estimator 未初始化，
低频刷新无从推进，挂件会永远显示冻结的旧快照。

现在启动时多一步：读**最近一条事件的 `raw_data`**，重建 estimator 并推进到"现在"。

**关键设计：只重建模型，不把历史观察塞进 `self.observations`。**
否则用户一打开就会看到上次的曲线，误以为是本次记录。曲线仍然只在真正开始记录后出现。

- 数据源是已有表（`emotion_events.raw_data`），**不需要新表**；
- 超过 7 天的旧事件不用于恢复（"太久以前的事不该影响现在"）；
- 失败（无事件/损坏/过期）就静默跳过，不影响启动。
