## 2. 做了什么

### 2.1 内核：抽出单步原语 `predict_step()`

`predict_forward()` 原来把"构造 F/Q → 循环推进 → 收集轨迹"揉在一个函数里，
没有单步入口。想增量推进，就只能每秒把整条尾巴从 `last_obs` 重算一遍。

新增 `emowave/core/inference/dynamics.py::predict_step()`：

```python
predict_step(state, cov, params, dt, mean=(0.5, 0.5), transition=None, noise=None)
    → (state', cov')
```

- 内部做**偏离空间**变换（与 `predict_forward` 同一套语义）；
- `transition` / `noise` 可选传入：批量调用时 F/Q 只构造一次，不拖慢 `predict_forward`；
- `predict_forward()` 改为循环调用它——**输出逐位一致**（见 §3 验证）。

### 2.2 presenter：尾巴改成增量

```python
self._tail = {"x": ..., "P": ..., "horizon": 0.0, "pts": []}
```

每个 tick 只推 `horizon - 已推` 的那一段（通常正好 1 秒），把新点追加到 `pts`。
单 tick 成本从 `O(horizon)` 降到 `O(Δt)`，累计从 `O(h²)` 降到 `O(h)`。

**作废条件**（必须重置，否则尾巴会画错）：
- 新一波开始；
- 基线变化（`nudge` / `fork` / `reset`）——均值变了，旧终点不再适用；
- 换人群 / `_end_wave`。

`_decay_points(horizon)` **保留原样**（从零重算）：它被测试直接调用，
语义是"给定 horizon 算一条完整尾巴"，与"增量推进"是两件事。
两者共用 `predict_step`，数学等价（测试断言终点一致到 1e-9）。

## 3. 验证

### 3.1 重构不改变数学（逐位比对）

重构前后用同一输入跑 `predict_forward(horizon=30s, dt=1s)`，30 个点的
`valence / arousal / var_valence` **完全一致**（10 位小数逐位相同）。

### 3.2 性能（horizon=600s 时的单 tick 成本）

| 路径 | 单 tick | 累计 600 次 |
|---|---:|---:|
| 旧：每 tick 从零重算整条尾巴 | **15.62 ms** | ≈ 9.4 秒 |
| 新：只推新增的 1 秒 | **0.303 ms** | ≈ 0.18 秒 |
| 提升 | **52×** | 52× |

### 3.3 新增测试（3 条）

| 测试 | 断言 |
|---|---|
| `test_decay_tail_is_incremental` | 60 次 tick 的 `predict_step` 调用数在 55–70（线性），而不是 1830 |
| `test_decay_tail_matches_from_scratch` | 增量终点 == 一次性重算终点（1e-9） |
| `test_baseline_change_invalidates_tail` | 衰减中 `nudge` → 尾巴作废并以新基线重建 |

## 4. 没做的事（以及为什么）

**每条新观察仍会触发一次全量 RTS**（N=600 时约 126ms）。

不做的理由：

1. 它已经不再是"每秒一次"——Phase 1 之后一次拖动只产生 1 条自评，
   触发频率低了一到两个数量级；
2. 真正的解法是"节点网格平滑"（内核文档提过 N≈300 节点）或增量 RTS，
   属于曲线性能范畴，和 Phase 5 的显示精度/抽稀是同一件事，应该一起做；
3. 现在做，会为了一个低频路径引入两套平滑结果，反而增加不一致风险。

已记录在 `03-阶段2-统一查询.md` §7 与本文 §5，留给 Phase 5。
