> 日期：2026-10-19 · 基于 `562c5e5`（Phase 1 收尾）· 回滚锚点 `v4-phase0`

## 1. 做了什么

把"某个时刻的状态"和"某段时间的曲线"收成**一个入口**，主窗、挂件、未来的定时刷新都问同一个对象：

| 能力 | 入口 | 说明 |
|---|---|---|
| 单点状态 | `presenter.query.query_state(ts)` | Phase 1 已有：推进模型时间，不产生观察 |
| 一段曲线 | `presenter.curve_payload(start, end, resolution)` | **本阶段新增**：窗口裁剪 + 降采样 + 缓存 |
| 视图取数 | `presenter.current_curve_payload()` | 退化为 `curve_payload()` 的别名（保持旧契约） |

`StateQuery.query_curve()` 的实现：`RTSSmoother.smooth()` → 按窗口裁剪 → 按 `resolution` 抽稀 → 组装 payload。
**降采样只影响画多少点，不影响模型精度**（平滑仍基于全部观察）。

## 2. 缓存：解决什么、不解决什么

`curve_payload()` 用一组键做缓存：

```python
(观察数, 纠正数, id(params), 基线效价, start_ts, end_ts, resolution)
```

任一变化才重算，否则直接返回上次的对象（`is` 相同）。

### 解决的

- **主窗 + 挂件同时取数**：以前各算一遍 RTS，现在算一次、两边共用同一份 payload。
- **反复查询**（切页、刷新、恢复后初始同步）：0 次重算。
- 实测：连续 3 次查询（含 `current_curve_payload()`）→ **0 次 `smooth()` 调用**。

### 不解决的（Phase 3 的事）

**每来一条新观察，缓存必然失效，仍要全量重算 O(N)。**
N=600 时一次 RTS 约 126ms——这条没变。缓存只是"同一份数据别算两遍"，
不是"新数据别全量算"。

> 好在 Phase 1 之后观察不再按秒产生（一次拖动 = 1 条），
> 所以"每秒 126ms"的场景在真实使用中已经不成立；
> 但连续自评 600 次后，每条仍会卡 126ms，Phase 3 要处理。

## 3. 为什么 `query_curve` 不带预测段

计划里写的是"获取历史曲线 + 生成预测区间"。实施时**故意没做预测段**：

- 预测段现在由 `_decay_points(horizon)` + `_emit_curve(points=...)` 负责，
  它的成本随 horizon 线性增长（Phase 0 实测 5s→0.21ms，600s→13.56ms）；
- 若把预测段塞进 `query_curve`，那么每次查询都会重算整条尾巴，
  等于把 Phase 3 要修的问题提前复制一份；
- 5 分钟刷新（Phase 4）才真正需要"历史 + 预测"一次取全，
  届时应该做成**单步增量**，而不是在查询层重算。

所以 Phase 2 只交付历史曲线；预测段在 Phase 4 与刷新调度一起设计。

## 5. 测试

| 测试 | 断言 |
|---|---|
| `test_curve_payload_respects_window_and_resolution` | 只返回窗口内的点，且点数 ≤ resolution（首尾保留） |
| `test_curve_payload_default_covers_all` | 不传窗口 = 全量 |
| `test_curve_cache_reuses_result_without_changes` | 三次查询 → 0 次 `smooth()`，且返回同一对象 |
| `test_curve_cache_invalidated_by_new_observation` | 新增观察 → 恰好重算 1 次 |
| `test_curve_payload_none_when_insufficient` | 少于 2 条返回 None |

**过程中修掉一个自己写的 bug**：第一版 `_decimate` 用 `int(i*step)` 再并上末尾索引，
会返回 `cap+1` 个点（31 点抽 10 点 → 11 点）。测试直接抓到了，改为
`step = (count-1)/(cap-1)` + `round`，保证恰好 `cap` 个。
