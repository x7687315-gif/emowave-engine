# 修复报告：点击「纠正」闪退（2026-10-25）

## 一句话结论

"点纠正闪退"属于 **PyQt5 槽内未捕获异常 → 进程静默终止** 这一整类故障：按钮回调里
任何一行代码抛出的 Python 异常，在 PyQt5 ≥5.5 的默认行为下都会在打印 traceback 后
调用 `qFatal` 终止进程——用户看到的就是"窗口消失、无任何提示"。而本应用此前
**没有崩溃日志、没有异常兜底、纠正弹窗 0 条测试覆盖**，所以任何一个潜伏问题都会以
"闪退"收场且无从追查。本次修复把这一类问题整体消除：**应用不再因任何槽内异常退出，
异常全部落盘 `~/.emowave/logs/` 并给出可见提示**；同时加固了纠正链路上发现的所有
隐患，并为弹窗补上了第一批 19 条测试。

## 排查过程（为什么定位到"这一类"而不是某一行）

1. **通读全项目**（入口 / windows / presenters / theme / curve_widget / 内核
   estimator / RTS / calibrator / db / 快照层），静态审出若干可疑点。
2. **离屏与真实 Windows 平台逐层复现**，覆盖以下场景全部通过：
   - 新会话 3 点记录 → 点纠正 → 弹窗 → 拖点 → 提交 → 再次打开；
   - 记录中打开纠正；60 点长记录；悬浮窗可见时纠正；
   - **用户真实数据库副本 + 用户最后一段真实数值（效价 0.25/唤醒 0.15）的精确重放**；
   - 真实 `.click()` 点击按钮与 QTest 合成鼠标事件（按下/拖动/释放/提交按钮）。
3. **关键证据**：项目 769 条测试中没有任何一条构造过 `CorrectionSheet` /
   `CorrectionCanvas`（只测了 `correction_context()` 的打包结构）；应用也没有任何
   崩溃捕获机制。也就是说：这条链路一旦在任何环境（不同 DPI/字体/输入法/打包版
   EXE/特定数据状态）踩中一个异常，**必然**表现为闪退，且事后零现场。
   复现脚本中人为制造的一个槽内异常确实让进程以 exit 127 无提示终止，印证了机制。
4. **结论**：与其猜某一行的环境特定触发条件，修复必须让这一类问题**结构性不可能**
   ——任何异常都不再把进程带走，并且下次发生时现场自动留档。

## 修复内容

### 1. 新增 `crashguard.py` —— 崩溃捕获（治本）

- 替换 `sys.excepthook`：PyQt5 文档化行为——**hook 被替换后不再 qFatal abort**。
  槽内未捕获异常改为：traceback 落盘 `~/.emowave/logs/crash-*.log` + 主窗口通知条
  提示 + **应用继续运行**。
- 开启 `faulthandler`（标准库）：原生段错误（无 Python traceback 的那类闪退）
  也留现场（`native-crash.log`）。
- `log_failure()`：已被调用方捕获的严重失败同样留档（`failure-*.log`），
  用户提示里的"详情已写入日志"是实话。
- 安全性：日志目录路径做了规范化 + 上级目录段拒绝；日志文件名白名单净化
  （`[A-Za-z0-9_-]`），并断言最终路径不逃出日志目录；用户提示只在主线程碰 GUI。
- 接线：`main()` 里在 `QApplication` 构造前 `install()`；`MainWindow` 把通知条
  注册为崩溃提示回调。

### 2. `windows/main_console.py` —— 纠正入口加固

- `_open_correction_sheet` 全链路 try/except：任何异常记录日志（`logger.exception`
  + `crashguard.log_failure`）并走通知条提示，**绝不外泄到 Qt 槽层**（外泄=闪退）。
- 无可纠正数据时不再静默返回（此前按钮是"死的"）：给出
  "还没有可纠正的曲线：先「开始记录」……"的可见提示。
- **模态期间暂停节律**：弹窗开着时 presenter 的 1Hz 心跳与低频刷新照跑，
  波可能在对话框期间衰减结束并清空 `states`，导致用户提交的纠正被静默丢弃；
  现在 `exec_()` 前后成对调用新增的 `pause_wave_timers()` / `resume_wave_timers()`
  （`finally` 保证异常路径也恢复）。

### 3. `windows/correction_sheet.py` / `correction_canvas.py` —— 隐患清除

- `_on_drag` 里的 `if idx == self._selected_index` 恒真死分支（赋值先行），
  重写为"拖动即选中 + 输入框同步 + 数值钳制到 [0,1]"。
- `_on_select` / `_on_drag` / `_on_manual_edit` 增加索引越界守卫。
- 画布 `mouseMoveEvent` 的长度守卫从 2 个序列补齐到 3 个（`model_a` 此前缺失）；
  `paintEvent` 的编辑点叠层与选中点叠层同样补齐（脏索引跳过绘制而不是抛异常）。

### 4. 测试：769 → 788（全部通过）

- **`tests/test_correction_sheet.py`（13 条，首次覆盖弹窗本体）**：构造与选中、
  拖动更新编辑/输入框/画布、数值钳制、越界索引忽略、手动输入需先选中、
  提交打包 `(ts, v, a)`、画布最近点命中、残缺序列（时间戳长于数值序列）下
  交互与重绘不抛异常、无数据点击给出提示、模态期间心跳暂停且结束后恢复、
  **构造异常被吞掉并提示且节律恢复**、提交 → ingest → 曲线重拟合全链路。
- **`tests/test_crashguard.py`（6 条）**：excepthook 替换生效、崩溃日志落盘、
  通知触发、`log_failure` 留档、目录穿越输入被拒、文件名净化。

### 5. 验证

- 全量 `pytest -q`：**788 passed**（原 769 + 新 19，无一条回归）。
- 真实 Windows 平台端到端验证：向纠正链路注入 `RuntimeError` 后点击按钮——
  旧代码进程消失；新代码**应用存活、通知条提示、failure 日志落盘、exit 0**。
- 架构护栏全绿：无孤儿模块、内核零依赖、LOC 26,168 / 预算 27,000。

## 事故披露：排查期间对本地数据库的误写与清理

排查中使用 `MainWindow(db=None)` 复现时，触发 `main_app.py` 的回退分支
（db 为 None 时自动打开 `~/.emowave/emowave.db`），导致合成测试数据写入了
**本机真实数据库**。已完整清理并核对：

- 删除了测试写入的 14 条合成事件（id 6–19，其样本时间戳完全相同，与真实事件
  一眼可辨）与 66 行合成预测日志；用户的 5 条真实事件（2026-09-19 至
  2026-10-25）原样保留。
- `active_wave` / `latest_state` 快照被测试覆盖过，已清空——应用下次启动会按
  设计从最近一条真实事件自动恢复，无需人工干预。
- 清理前已留全量备份：`~/.emowave/emowave.db.pre-cleanup-backup-20261025`。
- 本报告随附的教训已回灌到测试方法上：新增测试全部以 `db=None` 的
  `ConsolePresenter` 直接构造（不经过 MainWindow 的回退分支）。

## 修复后如果再遇到闪退怎么办

- 界面会弹通知条而不是消失；`~/.emowave/logs/` 里会有对应时间的
  `crash-*.log` / `failure-*.log` / `native-crash.log`，把日志内容反馈回来
  即可精确定位。
